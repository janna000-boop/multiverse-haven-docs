The Multiverse Haven · Feature Proposal

One Room.
Many Experiences.

A flexible Destination System for independent conversations, community boards, creative spaces, and fully customized pages.

Prepared by Fred · October 2026 · Concept only — not implemented or approved for deployment

VisionStructureTemplatesBlank CanvasSafetyFeasibilityRoadmap

01 · The Vision

Today, a Room is primarily a chat environment. We propose making it a home for multiple Destinations: individual spaces with distinct functions, content, layouts, and—where appropriate—independent conversations.

A Room is the community.
A Destination is where that community comes alive.

Destinations are not required to contain chat. A creator could offer a live gathering place, a journal, a quest board, a gallery, and an entirely custom page inside the same Room.

02 · How It Fits Together

Realm └── Settlement (when applicable) └── Room ├── Destination: Communal Table [Live Chat] ├── Destination: Fireside Alcove [Live Chat] ├── Destination: Kitchen Notices [Noticeboard] ├── Destination: Kitchen Journal [Community Board] ├── Destination: Story Basket [Story Prompts] └── Destination: Recipe Book [Blank Canvas]

Each Live Chat Destination has its own messages and presence. Visitors at the Communal Table are not automatically participants in the Fireside Alcove. A shared chat may be linked from multiple entry points without duplicating its history.

Tabs, doorways, cards, maps, and menus are possible navigation presentations—not different underlying storage models.

04 · Blank Canvas: Freedom to Create

Blank Canvas must be a first-class template, not an obscure advanced setting. It starts with an uncluttered page and allows ambitious creators to build original visual experiences.

  • Full CSS styling freedom inside an isolated Destination design surface.
  • Approved, sanitized HTML, CSS Grid/Flexbox, responsive layouts, typography, artwork and backgrounds.
  • Transitions and animations subject to accessibility and performance safeguards.
  • Live preview, draft publishing, safe reset, and ideally revision history.
  • Optional insertion of approved Haven components and navigation.

Safety boundary: “Full CSS control” must not mean styling the whole Haven site or overriding login, privacy, moderation, and security controls. Arbitrary JavaScript with Haven application privileges is out of scope for the initial release. Isolation needs technical review.

05 · Permissions, Continuity & Moderation

Room-wide permissions remain authoritative. Destination-specific rules can add restrictions, never silently bypass Room bans or privacy. Backend access checks must protect direct URLs as well as visible links.

  • Owner, moderator, reader, and contributor capabilities.
  • Destination visibility and publication controls.
  • Independent chat histories and accurate presence lists.
  • Reporting and moderation for visitor-submitted content.
  • Existing conversations and user data preserved during migration.
  • SQLite and PostgreSQL compatibility verified before deployment.

A creator who wants only one ordinary chat must still be able to run a simple Room without unnecessary complexity.

07 · Proposed Development Passes

  1. Design: Template catalog, creator workflow, navigation and visual prototypes.
  2. Information Destinations: Destination container, simple static templates and default entry.
  3. Independent Chat: Isolated messages, presence, privacy and moderation per chat Destination.
  4. Community Templates: Journals, corkboards, events, galleries and publishing permissions.
  5. Advanced Creator Tools: Sandboxed Blank Canvas, approved effects, audio and widgets.

Existing Rooms should retain their current chat as the default Destination through a tested compatibility or migration path. No production changes are authorized by this proposal.

08 · Design Commitments

Freedom. Creators choose function as well as appearance. Accessibility. Visitors can always understand where they are. Identity. Destinations can look radically different. Continuity. Changing a template must not erase content. Safety. Permissions remain enforceable. Simplicity. One chat remains easy. Extensibility. New templates fit without a wholesale rewrite.
